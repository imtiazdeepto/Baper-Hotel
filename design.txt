Build the actual frontend using semantic HTML5, modern CSS3, Bootstrap 5
utilities/components where useful, and vanilla JavaScript ES modules. Do

Read the assessment screenshots supplied by the user. The main ordering

============================================================ 1. DESIGN
GOALS ============================================================

Primary goals: 1. Make browsing and ordering food simple and fast. 2.
Make the cart and total bill easy to understand. 3. Make order status
easy to follow. 4. Make admin tasks clear and efficient. 5. Make the
interface responsive and accessible. 6. Keep visual design consistent
across every page. 7. Make the project look polished enough for a
university capstone demonstration.

Design principles: - Clarity over decoration. - Consistency over
novelty. - Strong visual hierarchy. - Visible feedback after every
important action. - Minimal steps to complete an order. - Never hide
important prices, status, errors, or actions. - Use real HTML text and
controls rather than text embedded in images.

============================================================ 3. SPACING,
GRID, AND RESPONSIVE BREAKPOINTS
============================================================

Desktop (>= 1200px): - Left sidebar: approximately 76px fixed width. -
Main content: flexible. - Right cart: approximately 320px fixed width. -
Main page horizontal padding: 28–36px. - Food grid: 3 columns, or 4 when
the viewport is wide enough. - Main content and cart should fit without
horizontal scrolling.

Tablet (768px–1199px): - Sidebar: 64px or collapsible. - Cart:
collapsible drawer or a separate cart section. - Food grid: 2 columns. -
Reduce main content padding to 20px.

Mobile (< 768px): - Use a compact top navigation or bottom navigation. -
Main content uses one food-card column or two columns only when cards
remain readable. - Cart becomes a dedicated page or slide-up drawer. -
Checkout fields stack vertically. - Buttons should have touch targets of
at least 44x44px. - No horizontal page scrolling. - Keep important
actions visible and easy to tap.

Use CSS Grid and Flexbox. Avoid fixed widths that break small screens.
Use max-width and minmax() where appropriate.

C. CHECKOUT PAGE - Page title and simple step indicator: Cart → Checkout

In, Pickup, Delivery (as configured). - Delivery address appears only

summary at the side on desktop and below form on mobile. - Show final
total prominently. - Submit button label: “Place Order”. - Show loading

D. ORDER CONFIRMATION PAGE - Clear success icon/state. - “Your order has
been placed”. - Unique order number. - Order summary. - Current order

E. ORDER TRACKING PAGE - Order number and order date. - Status timeline:
Pending → Confirmed → Preparing → Ready → Out for Delivery (if delivery)
→ Completed. - Cancelled state should be visually distinct. - Show item
list, total, payment method, and order type. - Refresh status from
Supabase or provide a refresh action. - Customers can only view their
own orders.

F. CUSTOMER ORDER HISTORY PAGE - Table/list of previous orders. -
Columns/cards: order number, date, total, status, action. - Filters by
status/date if practical. - Empty state for new customers. - Order
detail action.

G. LOGIN AND REGISTRATION PAGES - Simple centered form or split-screen
layout. - Restaurant branding and short welcome text. - Email and
password fields. - Register also asks name and phone if needed. - Show
password visibility toggle. - Inline validation and authentication
errors. - Link between login and registration. - Do not ask users to
select their own role. - Include accessible labels, not placeholder-only
labels.

H. ADMIN DASHBOARD - Admin sidebar with Dashboard, Foods, Categories,
Orders, Coupons, Reports, Logout. - Header with page title and admin
profile. - Summary cards: - Today’s orders. - Completed orders. -
Revenue. - Pending orders. - Recent orders table. - Sales chart if
useful. - Clear loading and no-data states. - Do not show fabricated
statistics; read actual Supabase data.

I. FOOD MANAGEMENT - Table or responsive list with food image, name,
category, price, availability, actions. - Search and category filter. -
Add Food button. - Add/edit form: - Name. - Description. - Category. -
Price. - Image upload. - Availability. - Image preview before upload. -
Confirm destructive actions. - Use soft deletion/deactivation where
historical orders must be preserved.

J. CATEGORY MANAGEMENT - Category list. - Add/edit category form. -
Delete only when safe; explain if foods are assigned. - Prevent

K. ORDER MANAGEMENT - Tabs or filters for Pending, Confirmed, Preparing,
Ready, Completed, Cancelled. - Order table with order number, customer,
date, amount, type, status, and details action. - Order details
drawer/page with ordered items and status controls. - Staff should see

feedback.

L. COUPON MANAGEMENT - Coupon table with code, type, value, expiry,
usage, active state. - Add/edit coupon form. - Clear active/expired
indicators. - Validate percentage and fixed discounts.

M. DAILY SALES REPORT - Date picker. - Summary metrics. - Daily sales
chart. - Detailed order table. - Clearly distinguish completed/paid
sales from pending orders. - Use real Supabase values.

============================================================ 6.
INTERACTION AND MICRO-INTERACTION REQUIREMENTS
============================================================

Every visible interactive element must work.

Examples: - Clicking category chips filters food. - Search filters the
food list. - Add to cart updates cart count and cart content. - Quantity
plus/minus updates line total and bill. - Remove deletes the cart
item. - Applying coupon displays success or a useful error. - Checkout
validates the form. - Buttons show loading state during network calls. -
Successful actions show a toast or inline success message. - Failed
requests show a useful error message. - Sidebar links navigate
correctly. - Mobile navigation opens/closes correctly. - Modal/dialog
can be closed with close button and Escape where practical. - Focus is
visible for keyboard users.

Do not use alert() for every interaction. Prefer accessible inline
feedback or toast messages.

Do not add inert buttons. If a feature is not implemented, do not
display a button suggesting it works.

============================================================ 7.
ACCESSIBILITY REQUIREMENTS
============================================================

-   Use semantic HTML: header, nav, main, aside, section, footer, form.
-   Use labels for all form controls.
-   Provide alt text for meaningful food images.
-   Use aria-label for icon-only controls.
-   Maintain sufficient color contrast.
-   Do not use color alone to communicate order status.
-   Ensure keyboard navigation works.
-   Provide visible focus styles.
-   Use correct button types.
-   Announce important dynamic cart/status updates with appropriate
    aria-live regions.
-   Respect prefers-reduced-motion.
-   Keep touch targets large enough on mobile.

============================================================ 11. FOOD
CARD DESIGN REQUIREMENTS
============================================================

Each food card should have: - Consistent food image size. - Optional
category label. - Food name. - Short description. - Price in BDT. -
Availability indicator. - Add to cart button. - Optional favorite action
only if implemented.

Image handling: - Use Supabase Storage image paths/URLs from the
database. - Use object-fit: cover. - Use a placeholder if an image is
missing. - Avoid distorted food photos. - Do not hotlink random images
from unknown sources in production. - Add alt text based on the food
name.

============================================================ 12.
RECOMMENDATION CARD DESIGN
============================================================

Each recommendation should display: - Food image. - Food name. -
Price. - Short recommendation reason. - Add button.

Examples of recommendation reasons: - “Often ordered with Onion Pizza” -
“Popular this week” - “Customers also choose this”

The UI must not claim that an item is frequently ordered unless the
recommendation service provides that reason.

The frontend should call the Supabase recommendation RPC described in
the backend prompt. It should refresh recommendations when cart contents
change, with a small debounce if necessary. It must not call the
recommendation function on every keystroke or create unnecessary
repeated requests.

If the recommendation function returns no results, hide the section or
show a polite fallback such as “More recommendations will appear as
customers place orders.” Do not hardcode fake recommendation results.

============================================================ 13. ADMIN
VISUAL DESIGN
============================================================

Admin UI should use the same brand tokens but prioritize information
density and clarity.

Admin layout: - Left admin sidebar (wider than customer icon-only
sidebar). - Topbar with page title and account menu. - Main content with
consistent max-width. - Summary metric cards. - Tables with clear
headers and row spacing. - Filters above tables. - Primary action in the
top-right of each management page. - Forms in cards or dedicated
pages. - Destructive actions require confirmation. - Status badges use
both text and color.

Avoid: - Too many dashboard cards. - Decorative charts with no business
meaning. - Fake data. - Tables that overflow mobile screens without a
responsive strategy. - Tiny text.

For mobile admin tables, use horizontally scrollable containers or
transform each row into a readable card layout.

============================================================ 14. FORM
DESIGN AND VALIDATION
============================================================

All forms must: - Have a visible label. - Show required fields. -
Display field-specific validation errors. - Preserve entered values
after recoverable errors. - Disable submit while saving. - Show
success/error feedback. - Use correct input types and autocomplete
attributes. - Use appropriate min/max constraints for prices,
quantities, and dates. - Never use placeholder text as the only label.

For image upload: - Show image preview. - Show allowed formats and size
limit. - Show upload progress if possible. - Show upload failure. -
Allow replacing/removing image if authorized.

============================================================ 15.
LOADING, EMPTY, ERROR, AND SUCCESS STATES
============================================================

Every Supabase-driven page must support: - Initial loading skeleton. -
Empty state. - Error state with retry action where appropriate. -
Success feedback after mutation. - Disabled/loading button while request
is running. - Offline/network failure message where practical.

Never leave a blank screen while data loads. Never show fake sample
records as if they came from the live database. Seed data may be used
for development, but label it as sample data.

============================================================ 16.
FRONTEND QUALITY AND PERFORMANCE
============================================================

-   Use semantic HTML.
-   Keep JavaScript in ES modules.
-   Keep Supabase client setup in one shared module.
-   Avoid duplicate network requests.
-   Debounce search input.
-   Use event delegation where appropriate.
-   Lazy-load food images below the fold.
-   Set width/height or aspect-ratio to reduce layout shift.
-   Avoid unnecessary dependencies.
-   Keep CSS maintainable and organized.
-   Avoid inline styles for repeated components.
-   Use consistent naming conventions.
-   Check browser console for errors.
-   Test keyboard navigation.
-   Test at common mobile widths.
-   Do not store secrets in localStorage.
-   Do not place service_role keys in browser code.
