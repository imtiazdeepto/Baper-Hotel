============================================================ 2. PROJECT
OBJECTIVE ============================================================

A small restaurant currently uses paper-based food ordering and wants a
digital ordering platform.

Customers should be able to: - Explore available food items. - Browse
food by category. - Search food items. - Add food to a shopping cart. -
Increase/decrease quantities and remove items. - View subtotal, coupon
discount, and final bill. - Place an order. - Select a payment method. -
Track order status. - View order history.

Restaurant administrators and staff should be able to: - Manage food
items and categories. - View incoming orders. - Update order status. -
Manage discount coupons. - View daily sales reports. - Review customer
order history where authorized.

============================================================ 6. CORE
ASSESSMENT REQUIREMENTS — MUST IMPLEMENT
============================================================

1.  DISPLAY FOOD MENU — 7 MARKS

-   Display available food items with image, name, description, price,
    and category.
-   Do not allow unavailable food to be ordered.
-   Provide loading, error, and empty states.

2.  FOOD CATEGORY FILTERING — 5 MARKS

-   Include categories such as Pizza, Fast Food, Noodle, Dessert,
    Seafood, Sushi, and Ramen.
-   Include an All option.
-   Category filtering must work with search.

3.  SEARCH FOOD ITEMS — 5 MARKS

-   Search by food name and, where useful, description.
-   Combine search with category filters.
-   Show a no-results message.
-   Use safe query construction and avoid unsafe SQL string
    concatenation.

4.  ADD ITEMS TO SHOPPING CART — 10 MARKS

-   Add food to the cart.
-   If already present, increase quantity.
-   Show cart item count.
-   Persist cart for logged-in customers using the database or a
    well-documented local cart approach.
-   Revalidate item availability and price when creating an order.

5.  INCREASE / DECREASE ITEM QUANTITIES — 5 MARKS

-   Provide plus/minus controls.
-   Minimum quantity is 1.
-   Provide remove action.
-   Update totals correctly.
-   Validate all values server-side/database-side.

6.  CALCULATE TOTAL BILL — 7 MARKS

-   Calculate subtotal from current database prices and quantities.
-   Calculate eligible discount.
-   Calculate final amount.
-   Use BDT (৳) by default.
-   Use PostgreSQL NUMERIC/DECIMAL for monetary values, never
    floating-point types.
-   Never trust a total, item price, or discount submitted by the
    browser.

7.  PLACE AN ORDER — 8 MARKS

-   Build a checkout page.
-   Collect customer contact and required order information.
-   Support Dine In, Pickup, and Delivery where practical.
-   Payment options: Cash, Debit Card, E-Wallet.
-   Unless a real payment gateway is configured, clearly label
    debit/e-wallet as demo/simulated methods. Do not claim money has
    been charged.
-   Create the order and order items atomically using a PostgreSQL
    function/RPC or another secure transaction-based server-side
    operation.
-   Recalculate prices and discounts using trusted database records.
-   Store item name and unit-price snapshots in order_items.
-   Generate a unique order number.
-   Prevent empty-cart checkout and duplicate submissions.

8.  ORDER TRACKING — 8 MARKS

-   Customers can view only their own orders.
-   Display order number, date, items, amount, payment method, and
    status.
-   Suggested statuses: Pending, Confirmed, Preparing, Ready, Out for
    Delivery, Completed, Cancelled.
-   Staff/admin can update statuses only with permission.
-   Record status history if practical.

9.  ADMIN FOOD MANAGEMENT — 8 MARKS

-   Protected admin dashboard.
-   Create, edit, list, deactivate, and delete food items as
    appropriate.
-   Manage categories.
-   Upload images to Supabase Storage.
-   Validate file type and size.
-   Use safe object names and Storage policies.
-   Preserve historical order details if a food item is deactivated or
    removed.

============================================================ 7. ADVANCED
ASSESSMENT FEATURES
============================================================

Implement these after all core features work.

A. DISCOUNT COUPON FUNCTIONALITY — 5 MARKS - Admin can

B. ORDER STATUS MANAGEMENT — 5 MARKS - Staff/admin can view and update
order status. - Record status changes and timestamps. - Enforce role

C. DAILY SALES REPORT — 5 MARKS - Admin can select a date and view daily

sales, discounts, and net sales. - Use a table and optionally
Chart.js. - Clearly define whether only completed/paid orders count as

D. CUSTOMER ORDER HISTORY — 5 MARKS - Show previous orders with date,
number, total, and status. - Allow viewing order details. - RLS must
ensure customers can only read their own history.

E. BONUS RECOMMENDATION FEATURE — 5 MARKS - Recommend popular or
complementary food based on cart contents. - ML is not required. -
Popular items can be derived from completed order-item counts. -
Complementary items can use simple category/rule-based mappings. -
Exclude items already in cart and unavailable items. - Show a reason
such as “Popular choice” or “Often ordered with pizza”.

============================================================ 10. ROW
LEVEL SECURITY (RLS) — CRITICAL
============================================================

Enable RLS on every table exposed through the Supabase Data API.

Write and test policies with least privilege.

Expected policy behavior: - Public/anonymous visitors may read active
categories and available food items only, if public menu browsing is
enabled. - Authenticated customers may read/update only their own
profile fields that are safe to edit. - Customers may read only their
own cart and cart items. - Customers may create and read only their own
orders and order items. - Customers must not directly edit order totals,
payment status, or order status. - Customers may read only their own
order status history. - Staff may read orders needed for restaurant
operations and update only permitted status fields through a secure
operation. - Admin may manage foods, categories, coupons, and reports. -
Only authorized admin operations can assign or change roles. - Anonymous
users must not read private customer information. - Storage policies
must allow public reading of food images if the bucket is public, while
only authorized admins can upload, update, or delete food images.

Do not use a broad policy such as “authenticated users can do
everything”.

Avoid RLS recursion. If helper functions are used, define them with
careful security settings and a safe search_path. Explain why each
policy exists.

Do not expose service_role keys to the frontend. RLS is mandatory, not
optional.

============================================================ 11. SECURE
ORDER CREATION AND DATABASE FUNCTIONS
============================================================

Do not let the browser directly insert arbitrary order totals or item
prices.

Implement a PostgreSQL function/RPC such as create_order that: - Uses
the authenticated user identity (auth.uid()). - Accepts only necessary
customer inputs, order type, payment method, coupon code, and cart item
identifiers/quantities. - Reads actual food prices and availability from
the database. - Validates positive quantities and available food. -
Recalculates subtotal and coupon discount in the database. - Creates
order and order_items in one database transaction (a PostgreSQL function
call is transactional). - Stores item-name and price snapshots. -
Updates coupon usage safely. - Returns the created order ID and order
number. - Rejects unauthorized or malformed requests.

Use a secure search_path and appropriate function permissions. Revoke
execution from roles that should not call the function and grant only
the necessary roles. Do not mark a function SECURITY DEFINER unless
necessary; if used, explain and secure it carefully.

Implement status changes through a secure function or tightly scoped RLS
update policy so customers cannot change their own order status.

SUPABASE STORAGE — FOOD IMAGES
============================================================

Use a Storage bucket such as food-images.

Requirements: - Explain how to create the bucket in Supabase. - Decide
whether food images are public or private. Public read is acceptable for

the object path in the foods table. - Use Supabase Storage public URL
helper for public images, or signed URLs if private. - Handle missing
images gracefully. - Do not store large image binaries directly in
PostgreSQL.
