[BUG-01] JavaScript TypeError Halts Admin Dashboard Initialization
--------------------------------------------------------------------------------
Severity:       HIGH
Affected Route: /admin/dashboard.html
Component:      assets/js/admin.js:60
Description:
  On admin dashboard initial load, an uncaught TypeError was thrown:
  "TypeError: Cannot set properties of null (setting 'textContent') at initDashboard (admin.js:60:33)"
Evidence:
  assets/js/admin.js queried document.getElementById('dash-coupons-count'), but 
  admin/dashboard.html only contained:
    - dash-revenue
    - dash-orders-count
    - dash-pending-count
    - dash-foods-count
  The missing DOM element caused execution of initDashboard() to abort midway, 
  leaving loadRecentOrders() uncalled. As a consequence, the "Recent Orders" table 
  was permanently stuck displaying "Loading recent orders...".
Root Cause:
  Direct property assignment to null element without defensive check or element 
  existence in HTML.
Fix & Verification:
  1. Updated assets/js/admin.js to defensively check all KPI element handles before 
     assigning textContent.
  2. Verified live with browser subagent: dashboard metrics, KPIs, and Recent Orders 
     table rendered cleanly without console exceptions.
Status: RESOLVED

[BACKEND-06] Kitchen Order Confirmation Revenue Disconnection on Admin Dashboard
--------------------------------------------------------------------------------
Severity:       HIGH
Affected Route: /admin/dashboard.html
Component:      assets/js/admin.js:50-65, admin/dashboard.html:101-108
Description:
  When an order was confirmed in the Kitchen Queue (/staff/orders.html), the 
  Admin Dashboard revenue did not connect or update, remaining at ৳ 0.00.
Evidence:
  assets/js/admin.js strictly calculated revenue using:
    const completedOrders = orders.filter(o => o.order_status === 'Completed');
  When kitchen staff clicked "Confirm Order", the order status became 'Confirmed' 
  (and subsequently 'Preparing', 'Ready', 'Out for Delivery'). Because the status 
  was not yet 'Completed', the revenue calculation completely ignored active orders.
Root Cause:
  Metric filtered only terminal 'Completed' orders instead of all active, confirmed, 
  and non-cancelled orders.
Fix & Verification:
  1. Updated assets/js/admin.js to calculate Total Sales Revenue across all 
     non-cancelled orders (orders.filter(o => o.order_status !== 'Cancelled')).
  2. Updated admin/dashboard.html label from "Realized Revenue (from completed orders)" 
     to "Total Sales Revenue (from confirmed & active orders)".
  3. Verified: as soon as kitchen staff confirms an order, the revenue immediately 
     connects and increments on the dashboard.
Status: RESOLVED

[BACKEND-07] Admin Coupon Creation Fails on Check Constraints & Expiry Timezones
--------------------------------------------------------------------------------
Severity:       HIGH
Affected Route: /admin/coupons.html
Component:      assets/js/admin.js:615-645, admin/coupons.html
Description:
  When admins attempted to create a new coupon in the Admin Portal, coupon creation 
  failed or the created coupon was not accepted by the checkout system.
Evidence:
  1. Database check constraints in public.coupons enforce:
     - CHECK (maximum_discount IS NULL OR maximum_discount > 0)
     - CHECK (usage_limit IS NULL OR usage_limit > 0)
     If an admin left Max Cap or Usage Limit blank or entered 0, the form sent 
     0 or NaN, triggering PostgreSQL constraint violations (code 23514).
  2. HTML datetime-local produced local timestamps without timezone offsets. In UTC 
     cloud databases, slight clock drift or timezone differences caused validate_coupon 
     to reject coupons with "This coupon has not started yet" (NOW() < start_date).
Root Cause:
  Unsanitized non-positive numerical values and lack of ISO-8601 UTC timestamp formatting.
Fix & Verification:
  1. Sanitized maximum_discount and usage_limit: if empty, 0, or non-positive, passed NULL.
  2. Formatted expiry_date using new Date(raw).toISOString().
  3. Set start_date explicitly to 1 minute in the past (Date.now() - 60000) so newly 
     created coupons are immediately active without clock drift issues.
  4. Added button spinner and user alert on successful creation.
  5. Tested: created coupons save cleanly and apply instantly during checkout.
Status: RESOLVED

[BACKEND-09] Order Confirmation Subtotal Delay & Cart Calculation Hardening
--------------------------------------------------------------------------------
Severity:       MEDIUM
Affected Route: /order-confirmation.html, /checkout.html, assets/js/cart.js
Component:      assets/js/checkout.js:278, assets/js/orders.js:33-45, assets/js/cart.js:112
Description:
  When an order was submitted and redirected to /order-confirmation.html, the Subtotal 
  and Total fields initially showed "৳ 0.00" until the asynchronous Supabase query 
  resolved. Additionally, calculateSubtotal() could produce NaN if any cart item price 
  was passed as a raw string without parsing.
Root Cause:
  Only order_id and order_number were passed in the redirect query parameters; 
  amounts were dependent on network roundtrip.
Fix & Verification:
  1. Updated checkout.js to pass subtotal, discount, and total in redirect query parameters.
  2. Updated orders.js to render subtotal, discount, and total immediately on page load.
  3. Hardened calculateSubtotal() in cart.js with parseFloat(item.price) || 0 and 
     parseInt(item.quantity) || 1.
Status: RESOLVED

5. SECURITY & DATA INTEGRITY AUDIT
--------------------------------------------------------------------------------
- Row Level Security (RLS):
  * public.profiles: Authenticated users view own row; role escalation blocked 
    via RLS check (auth.uid() = id AND role = current_role).
  * public.orders: Customers view only their own orders; staff/admin view all.
  * public.track_order: SECURITY DEFINER RPC permits tracking strictly by unique 
    cryptographic order number without leaking customer credentials.
- Financial Calculations:
  * Prices and totals are never trusted from client-side JS; recalculated strictly 
    inside PostgreSQL create_order RPC using database price snapshots.
  * Monetary columns strictly use NUMERIC(10,2) (no IEEE-754 floating point drift).
- Credentials Hygiene:
  * Public client bundle only contains public anon key.
  * No service_role key or plain-text user passwords exposed.
